# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Socratic Terminal (苏格拉底终端)** is an AI-powered deep discussion tool built on Godot 4.4+. It enables users to engage in profound conversations with up to 8 AI "thinkers" (each with distinct personalities) who discuss topics from multiple angles until the user fully understands.

**Key Concept**: Unlike typical chatbots, this system orchestrates multi-agent AI discussions where AIs debate, critique, and refine each other's explanations. A depth analysis system ensures discussions go beyond surface-level responses to explore underlying principles, edge cases, and practical applications.

2. **Run**: Press F5 in Godot editor to launch the terminal interface

## Architecture Overview

### Singleton Managers (Autoloaded)
The system uses Godot's autoload for global managers (see [project.godot:18-23](project.godot#L18-L23)):

1. **SettingsManager** ([script/ui/SettingsManager.gd](script/ui/SettingsManager.gd))
   - Manages configuration persistence
   - Stores AI agent settings (API keys, models, prompts)
   - Persists to `user://settings.cfg` and syncs with AgentManager

2. **APIManager** ([script/ai/APIManager.gd](script/ai/APIManager.gd))
   - Creates HTTPRequest nodes for AI API calls
   - Fetches per-agent settings from SettingsManager
   - Uses APIConfig for provider-specific request formatting
   - Auto-cleanup: HTTPRequest nodes self-destruct after completion

3. **AgentManager** ([script/ai/terminal/AgentManager.gd](script/ai/terminal/AgentManager.gd))
   - Manages up to 10 AI agent configurations
   - Provides 8 preset persona templates (Socratic, Critic, Theorist, etc.)
   - Loads/saves agent configs from `user://agents.json`
   - Emits `agents_changed` signal on configuration updates
   - Supports environment variable expansion for API keys (`${ENV:OPENAI_API_KEY}`)

4. **MultiAgentOrchestrator** ([script/ai/terminal/MultiAgentOrchestrator.gd](script/ai/terminal/MultiAgentOrchestrator.gd))
   - Orchestrates multi-agent discussions
   - Manages conversation turns and history
   - Constructs AI prompts with depth-awareness
   - Performs periodic depth checks (every 5 turns)
   - Detects user "I understand" signals to end discussions

### Core Systems

#### API Configuration System

**APIConfig** ([script/ai/APIConfig.gd](script/ai/APIConfig.gd)) is a static configuration class:

- **Supported Providers**: Ollama, OpenAI, DeepSeek, Doubao, Gemini, Claude, KIMI, OpenAI-Compatible
- **Request Formats**: Maps providers to format types (`ollama`, `openai`, `gemini`, `claude`)
- **Response Parsing**: Unified `parse_response()` handles different API response structures
- **Dynamic Headers**: Builds provider-specific headers with API key substitution

**Key Methods**:
- `get_api_types()`: Returns all available provider names
- `build_request_data(api_type, model, prompt)`: Creates provider-specific request body
- `build_headers(api_type, api_key)`: Generates headers with authentication
- `parse_response(api_type, response, character_name)`: Extracts text from API responses

#### AI Agent System

**Agent Personas** (8 presets in [AgentManager:112-198](script/ai/terminal/AgentManager.gd#L112-L198)):
- **苏格拉底 (Socratic)**: Guides through questioning, reveals assumptions
- **批判者 (Critic)**: Challenges arguments, finds logical flaws
- **综合者 (Synthesizer)**: Integrates viewpoints, builds frameworks
- **实践者 (Pragmatist)**: Focuses on practical implementation
- **理论家 (Theorist)**: Explores mathematical principles and rigor
- **类比大师 (Analogist)**: Uses metaphors and cross-domain analogies
- **魔鬼代言人 (Devil's Advocate)**: Deliberately argues opposing views
- **学术派 (Scholar)**: Cites authoritative sources and historical context

Each agent has:
- `name`: Display name
- `api_type`: AI provider (OpenAI, Claude, etc.)
- `model`: Specific model name
- `api_key`: API key (supports environment variables)
- `system_prompt`: Persona definition
- `color`: Terminal display color
- `enabled`: Whether agent participates
- `is_moderator`: Whether agent leads/summarizes

#### Depth Analysis System

**DepthAnalyzer** ([script/ai/terminal/DepthAnalyzer.gd](script/ai/terminal/DepthAnalyzer.gd)):

Evaluates discussion quality along three dimensions:

1. **Keyword Depth** (40% weight):
   - Positive keywords: "本质"(1.5), "原理"(1.5), "反例"(1.5), "矛盾"(1.4)
   - Negative keywords: "差不多"(-0.8), "我觉得"(-0.4)
   - Score = Σ(keyword_weights) / (total_chars/100)

2. **Concept Layers** (30% weight):
   - Layer 1: Surface phenomena ("现象", "表面")
   - Layer 2: Mechanisms ("原因", "机制")
   - Layer 3: Principles ("本质", "原理")
   - Layer 4: Axioms ("公理", "假设")
   - Score = layers_detected / 4

3. **Critical Interactions** (30% weight):
   - Detects phrases like "你说的有问题", "忽略了", "纠正"
   - Score = min(interaction_count / 5, 1.0)

**Pass Criteria**:
- Depth score ≥ 0.6
- Concept layers ≥ 2
- Critical interactions ≥ 3

If depth is insufficient, system prompts AIs to explore principles, counterexamples, and applications.

#### Terminal UI System

**TerminalChat** ([script/ai/terminal/TerminalChat.gd](script/ai/terminal/TerminalChat.gd)):

- Linux-style terminal interface using RichTextLabel with BBCode
- Command parser for `/agents`, `/topic`, `/export`, etc.
- Markdown-to-BBCode converter supporting:
  - Code blocks (```code```)
  - Inline code (`code`)
  - Bold (**text**)
  - Italic (*text*)
  - Quotes (> text)
- Auto-scrolling and color theming
- Conversation export to `docs/runing/`

### Data Flow: How a Discussion Works

```
1. User Input
   ↓
   TerminalChat receives topic
   ↓
2. Start Discussion
   ↓
   MultiAgentOrchestrator.start(topic)
   - Clears history
   - Emits discussion_started
   - Enters debate loop
   ↓
3. Agent Turns (Round-robin)
   ↓
   For each enabled agent:
     - Build prompt with:
       * Agent persona (system_prompt)
       * Topic
       * Discussion rules (depth guidelines)
       * Recent history (last 12 messages)
       * Current task (from depth analysis)
     - Call APIManager.generate_dialog()
     - Parse response via APIConfig
     - Append to history
     - Emit line_emitted signal
     - Delay 0.2s
   ↓
4. Depth Check (every 5 turns)
   ↓
   DepthAnalyzer.assess_depth(history)
   - If insufficient: emit depth report + guidance
   - If sufficient: ask user "Do you understand?"
   ↓
5. User Interaction
   ↓
   User can:
   - Insert comments (/say)
   - Ask questions (triggers response)
   - Say "懂了" (I understand) → triggers stop
   ↓
6. Discussion End
   ↓
   When user confirms understanding:
   - Moderator generates summary
   - Emits summary_available
   - Emits discussion_stopped
   - Sets _active = false
```

## Common Development Tasks

### Adding a New AI Provider

1. Register in [APIConfig.gd:44-145](script/ai/APIConfig.gd#L44-L145):
```gdscript
_providers["NewProvider"] = APIProvider.new(
    "NewProvider",
    "Display Name",
    "https://api.example.com/v1/chat",
    ["model1", "model2"],
    true,  # requires_api_key
    {"Content-Type": "application/json", "Authorization": "Bearer {api_key}"},
    "openai",  # request_format
    "openai"   # response_parser
)
```

2. Add request format if needed in `build_request_data()`
3. Add response parser if needed in `parse_response()`

## Code Style

Following [CONTRIBUTING.md](CONTRIBUTING.md):
- **Naming**: snake_case for variables/functions, UPPER_CASE for constants, PascalCase for classes
- **Indentation**: Tabs (Godot default)
- **Comments**: Chinese comments acceptable (bilingual codebase)
- **Signals**: Prefer signals over direct function calls for inter-module communication

## Key Design Patterns

1. **Signal-Based Decoupling**: Managers communicate via signals
   - `agents_changed`, `discussion_started`, `line_emitted`

2. **Autoload Singletons**: Global access via `get_node("/root/ManagerName")`

3. **Static Configuration**: APIConfig uses static methods, no instance needed

4. **Self-Cleaning HTTP**: HTTPRequest nodes auto-delete after completion

5. **Environment Variable Support**: API keys support `${ENV:VAR}` expansion

## Known Issues & Limitations

1. **Sequential Agent Turns**: Currently round-robin; could optimize with intelligent scheduling based on topic relevance
2. **Token Usage**: Full conversation history sent each turn; could compress/summarize older messages
3. **No Rate Limiting**: API calls have no built-in throttling
4. **Memory Unbounded**: Conversation history grows without limits (only capped by MAX_TURNS)

## Testing Workflow

To test the full discussion flow:

1. Launch project (F5)
2. Set up agents:
   ```
   /agents key 苏格拉底 ${ENV:OPENAI_API_KEY}
   /agents key 批判者 ${ENV:ANTHROPIC_API_KEY}
   ```
3. Start discussion:
   ```
   什么是递归?
   ```
4. Observe:
   - Agents take turns (0.2s delay between)
   - Depth analysis every 5 turns
   - System prompts if depth insufficient
5. Interact:
   ```
   /say 我不太理解终止条件
   ```
6. End:
   ```
   懂了
   ```
7. Check export:
   ```
   /export 递归讨论
   ```

## Performance Considerations

- Each agent turn: ~500-1000 tokens prompt + ~200-500 tokens response
- 10-turn discussion with 3 agents: ~21k-45k tokens total
- Use cheaper models (gpt-4o-mini, deepseek-chat) for cost efficiency
- Local models via Ollama for free operation
